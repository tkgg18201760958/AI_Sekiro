# Sekiro RL Agent — 潜在困难与解决方案

配套文档：[architecture.md](./architecture.md)、[roadmap.md](./roadmap.md)

## 为什么放弃内存读取，改用画面读取为主

调研开源实现 `docs/案例/RL-Sekiro-env`（一个已跑通的只狼RL训练环境）后发现：

- 只狼没有现成、稳定、可以直接拿来用的公开内存偏移表。该案例要拿到角色/Boss的HP、架势值，靠的是 `pymem.pattern.pattern_scan_module` 做**特征码扫描**（在游戏模块里搜带通配符的opcode字节模式，定位到读血量/写伤害的汇编指令位置），再手写x86-64机器码做**运行时代码注入（hook）**，把游戏内部的角色/Boss结构体指针"偷"出来写到自己分配的内存里，最后在这个基址上加固定偏移（如 `+0x130` 是HP）读值。这不是"查表填地址"的难度，而是要理解游戏汇编、写字节码补丁、处理指针链的逆向工程活，且实现被硬编码死绑定在 `v1.06` 版本，版本更新后特征码和偏移大概率全部失效，需要重新逆向。
- 该案例作者自己也试过纯颜色识别血条（HSV阈值），但反馈"生命值/耐力值识别不准确，会有小波动，偶尔有大波动"，因此转向了内存方案。但这只说明**当时那一版画面识别做得比较粗糙**（只做了简单阈值匹配，没有做区域精确标定、多帧平滑、动态范围归一化），不代表画面识别路线本身走不通——只要把这些工程细节做扎实，可靠性可以明显优于那次尝试。

综合考虑开发门槛（逆向工具链 vs 图像处理）、版本脆弱性（绑定游戏版本 vs 分辨率/UI缩放）、以及对游戏进程的侵入性（代码注入修改游戏内存 vs 只读屏幕像素，后者更安全、不涉及修改游戏本体），画面读取的性价比明显更高，因此确定为**唯一规划的真实数据源**，不再规划内存读取模块。

## 潜在困难与解决方案

| 困难 | 说明 | 解决方案 |
|---|---|---|
| 画面坐标/颜色阈值随分辨率、UI缩放漂移 | 换一台机器、换分辨率、换DPI缩放设置，标定好的血条区域坐标和颜色阈值就会失效 | 用 `GetClientRect`（非 `GetWindowRect`）定位客户区避免标题栏/边框偏移；标定参数写入 `config.yaml` 而非硬编码；提供可视化标定脚本，换环境后可以快速肉眼重新校准并回归测试 |
| HP/架势条颜色识别有噪声（血条渐变、受击闪光、光照/特效干扰） | 单帧颜色阈值判断容易被瞬时视觉效果干扰，产生数值抖动 | 多帧滑动平均/中值滤波平滑输出；HSV阈值区间留够容差；对识别结果做单步最大变化量限制（防止一帧内血量"跳变"过大导致reward异常） |
| 精确坐标/距离在UI上不显示，画面方案拿不到 | `player_pos`/`boss_pos`/精确 `distance` 这类字段没有对应可见UI元素 | 从 observation 中去掉精确坐标字段，或退化为粗略的相对距离分档（近/中/远），基于锁定框大小或角色画面占比间接估计，不追求精确数值 |
| Boss "危"字等关键动作提示识别不稳 | 图标可能被特效遮挡、出现时间短、分辨率不同大小不同 | 模板匹配设多尺度候选；配合HP/架势瞬时变化趋势做交叉验证，而不是单一signal决策 |
| 键鼠输入被游戏反作弊/输入过滤 | 某些引擎不识别 pyautogui 等库的模拟输入 | 优先用 pydirectinput（DirectInput 扫描码），如仍无效考虑 vJoy/虚拟手柄方案 |
| 训练速度慢（真实游戏每步有延迟） | 真实环境一步可能几百毫秒，PPO 需要大量样本 | 阶段6前用 mock 环境跑通算法逻辑和超参；真实训练阶段考虑降低 total_timesteps 预期，或先用简单Boss/教程敌人预训练再迁移 |
| Boss战自动重开路径不稳定（读碑/走位差异） | UI/剧情节奏变化导致固定按键序列失效 | RestartManager 用状态驱动而非固定延时驱动，每步检测状态再决定下一按键；加超时兜底逻辑 |
| Reward 设计导致AI学到取巧策略（如一直后退） | 稀疏/不合理奖励导致收敛到无意义策略 | 阶段8专门做奖励调优；先用简单mock场景验证reward符号和量级再上真实训练 |
| 观察延迟与动作执行延迟不同步 | 截图+图像处理耗时导致决策基于过时状态 | 在 env.step 中显式记录并暴露 state 时间戳，后续可分析延迟影响；先保证功能正确，性能优化放最后 |
